# プラットフォーム設計: ハブ・ランチャー・モニター（案）

作成: 2026-10-16 / 状態: **設計確定、P-A・P-B 実装済み**（2026-10-16、11・12 章）。次は P-C（ランチャー）。

## 1. 背景と目的

利用者の要望（2026-10-16）:

- 今後、After Effects と Maya 以外のアプリとも相互に送れるようにし、タイムワープ以外の情報も送れるようにする
- 各種ツールを管理する **ランチャー**: アップデート、モニターの起動など
- **モニター**: 動作中のサーバーの一覧、ログの確認、サーバーの強制終了

今の SyncBridge（0.1.x）は、次の点がコードに直接書かれている。広げるには、まずここを一般化する必要がある。

| 場所 | 今の作り |
|---|---|
| `protocol.APPS` | `maya`、`ae`、`test` だけを受け付ける |
| `protocol.DIRECTIONS` | `maya2ae`、`ae2maya` の 2 方向だけ |
| `server/flow.py` の `EXPORT_KIND` | アプリごとに 1 種類のデータ（タイムワープ）だけ |
| `core/jobs.py` | タイムワープ専用の変換手順 |
| セッションファイル | 1 ユーザーに 1 つ（`session.json`）。サーバーは 1 つの前提 |

## 2. 用語

| 用語 | 意味 | 今の名前 |
|---|---|---|
| ハブ（Hub） | 各アプリの接続を受け、変換して中継する常駐プロセス。1 ユーザーに 1 つ | Local Sync Server、`SyncServer.exe` |
| アダプター | 各アプリの中で動き、ハブに接続する部分 | Maya の `syncbridge_maya`、AE の CEP パネル |
| データ種別（data type） | 送れる情報の種類。`timewarp`、`scene_settings`、`markers`、`camera` など | タイムワープだけ |
| ランチャー | 利用者が最初に開く管理アプリ。アップデートやモニターの起動 | なし |
| モニター | ハブの状態、ログ、転送の履歴を見て、止めたり切断したりする画面 | なし |
| アップデーター | 更新を取得・検証・適用する独立プロセス（仕様 10 章） | なし |

## 3. 全体構成

```
                ┌───────────── SyncBridge.exe（ランチャー + モニター、PySide6）───────────┐
                │  ランチャー: 構成とバージョン、更新、ハブの起動/停止、モニターを開く、フォルダ   │
                │  モニター  : ハブの一覧、接続中のアプリ、転送の履歴、ログ、停止/強制終了/切断   │
                └───────┬───────────────────────────────┬────────────────────────────────┘
          管理 API（HTTP/WS、トークン）│                     │ 起動
                        ▼                               ▼
   Maya ──┐      ┌──────────────── ハブ（SyncServer.exe）─────────────┐      SyncUpdater.exe
   AE ────┼─WS──►│  接続管理（アプリ + 能力の申告）                       │      （更新の取得・検証・
   Nuke ──┤      │  データ種別レジストリ（timewarp, scene_settings, …）   │       適用・ロールバック）
   …    ──┘      │  転送の手順（export → 中立形式 → 変換 → apply → 検証）   │
                 │  転送の履歴、ログ（リングバッファ + ファイル）           │
                 └──────────────────────────────────────────────────┘
```

- ハブは **ランチャーがなくても動く**（今どおり、アプリ側の Connect で自動起動）。ランチャーは管理のための道具で、必須にしない。
- ハブ、ランチャー、アップデーターは別のプロセス。どれかが固まっても、ほかから止められるようにする。

## 4. ハブの一般化（複数アプリ・複数データ）

### 4.1 能力の申告

`hello` に、そのアダプターが **出せる** データと **受け取れる** データを入れる。ハブはこれで「誰から誰へ何を送れるか」を判断する。

```json
{"kind": "hello", "data": {
  "token": "...", "app": "maya", "version": "2024", "pid": 1234, "document": "shot010.mb",
  "protocol": 2,
  "capabilities": {"export": ["timewarp", "scene_settings"], "apply": ["timewarp", "scene_settings"]}
}}
```

- `app` は固定の一覧ではなく、識別子（英小文字・数字・`_`）であれば受け付ける。表示名はアダプターが `app_label` で渡す。
- `capabilities` がない接続（0.1.x のアダプター）は `{"export": ["timewarp"], "apply": ["timewarp"]}` とみなす（後方互換）。

### 4.2 データ種別レジストリ（`core/datatypes/`）

データ種別ごとに、次の 4 つを登録する。アプリ間の変換は **アプリの形式 → 中立形式 → アプリの形式** で行う
（アプリが N 個でも変換は 2N 通りで済み、N×N にならない）。

| 要素 | 内容 | timewarp の場合（今のコード） |
|---|---|---|
| 中立形式 | アプリに依存しない表現 | `TimeCurve`（`core/curve.py`） |
| コーデック | アプリごとの「アプリ形式 ⇔ 中立形式」 | `maya_codec`、`ae_codec` |
| 文脈 | アプリ間の対応づけ（原点、fps など） | `MappingContext` |
| 検証 | 送る前の確認、送った後の読み戻し | `check_source_range`、`jobs.readback` |

新しいアプリを足す = そのアプリのアダプターと、扱うデータ種別のコーデックを足す。
新しいデータ種別を足す = 中立形式と、対応するアプリのコーデックを足す。

### 4.3 転送要求

```json
{"kind": "transfer.request", "data": {
  "data_type": "timewarp",
  "source": {"app": "maya"}, "target": {"app": "ae"},
  "options": {"mode": "editable", "origin": 1}
}}
```

- `source` / `target` は `app`（最後に接続したそのアプリ）か `client_id` で指定する。
- 0.1.x の `direction: "maya2ae"` は `data_type: timewarp, source: maya, target: ae` の別名として受け付け続ける。
- `export.request` / `apply.request` にも `data_type` を入れる。

### 4.4 1 PC に複数のハブ

普段は 1 ユーザーに 1 つ。ただし実際には、開発版とインストール版、異常終了後の残り、ポート違いなどで複数が動き得る
（Phase 1 の確認で実際に起きた）。モニターで見つけて止められるよう、セッションファイルを **ハブごと** にする。

- `%LOCALAPPDATA%\SyncBridge\hubs\<pid>.json`（ポート、トークン、バージョン、起動時刻、実行ファイル、実際のプロセスのイメージ）
  - 開発環境の venv では `sys.executable`（`.venv\Scripts\python.exe`）は基の python を子として起動するランチャーで、
    ハブのプロセスは別のファイル（基の `python.exe`）で動く。そのため、ハブが自分のイメージを `image` として記録する（P-A で判明）。
- `session.json` は「今使うハブ」を指すものとして残す（0.1.x のアダプターとの互換）

## 5. モニター

### 5.1 画面

| 区画 | 内容 |
|---|---|
| ハブの一覧 | 見つかったハブ（ポート、PID、バージョン、起動時刻、実行ファイル、応答の有無）。状態: 正常 / 応答なし / セッションファイルのみ残っている |
| 接続中のアプリ | 選んだハブにつながっているアプリ（アプリ、バージョン、文書、接続時刻、送れるデータ種別） |
| 転送の履歴 | 最近の転送（時刻、データ種別、送信元 → 送信先、結果、変換と読み戻しの誤差、メッセージ） |
| ログ | ハブのログ（リアルタイム表示、レベルで絞り込み、ログフォルダを開く） |

### 5.2 操作

| 操作 | 方法 | 確認 |
|---|---|---|
| ハブを停止 | 管理 API `POST /admin/shutdown`（接続中のアプリに通知してから終了） | 確認ダイアログ |
| ハブを強制終了 | 応答しないハブを OS のプロセス終了で止める。**SyncBridge のハブであること**（実行ファイルのパスかコマンドライン）を確かめてから | 確認ダイアログ（理由と PID を表示） |
| アプリを切断 | 管理 API `POST /admin/clients/{id}/disconnect` | 確認ダイアログ |
| 残ったセッションファイルを片付け | プロセスがないハブのファイルを削除 | 確認ダイアログ |

### 5.3 情報の取り方

- **ハブの発見:** `hubs\*.json` とプロセスの一覧（`SyncServer.exe`、`-m syncbridge.server`）を突き合わせる。どちらか片方にしかないものも表示する。
- **管理 API（ハブに追加）:** ループバックのみ、セッションファイルのトークンが必要（今の WebSocket と同じ扱い）。

| API | 内容 |
|---|---|
| `GET /admin/status` | バージョン、起動時刻、接続中のアプリ、データ種別、転送中かどうか |
| `GET /admin/transfers?limit=` | 転送の履歴（ハブの中に直近 200 件を保持） |
| `GET /admin/log?tail=` | ログの末尾（ハブの中に直近 2,000 行を保持。ファイルにも出す） |
| `WS /admin/events` | 接続・切断・転送・ログをリアルタイムで流す |
| `POST /admin/shutdown` | 正常終了 |
| `POST /admin/clients/{id}/disconnect` | アプリを切断 |

## 6. ランチャー

| 機能 | 内容 |
|---|---|
| 構成とバージョン | ハブ、アダプター（Maya / AE / …）、ランチャー自身のバージョン。インストール済みかどうか |
| 更新 | 更新の確認、内容の表示、適用（アップデーターを起動して自分は終了） |
| ハブ | 起動 / 停止、状態の表示 |
| モニター | モニターを開く |
| 連携の設定 | Maya へのボタン追加の案内（ドラッグ用ファイルを開く）、AE パネルの状態 |
| フォルダ | ログ、バックアップ、保存したタイムワープのフォルダを開く |

- 形は **普通のウィンドウ**（9 章）。常駐せず、開いたときに更新を確認する。
- インストーラーがスタートメニューとデスクトップにショートカットを作る（任意）。

## 7. アップデーター（仕様 10 章の具体化）

1. ランチャーが **更新情報**（マニフェスト）を取得: `{channel, version, notes, url, size, sha256, signature}`
2. 新しい版があれば内容を表示し、利用者が同意したら `SyncUpdater.exe` を起動してランチャーは終了する
3. アップデーター: ダウンロード → **SHA-256 と署名を検証** → ハブを止める → 今のインストールをバックアップ →
   インストーラーを静かに実行（`install.ps1 -Quiet`）→ バージョンを確認 → 失敗したらバックアップから戻す → ランチャーを再起動

- **真正性:** マニフェストに Ed25519 の署名を付け、公開鍵をランチャーに同梱する。秘密鍵は Git 管理外（`packaging/local/`）。
  ハッシュとパッケージが同じ場所にあるだけでは改ざんを防げない（仕様 10 章の注意）。
- **配布元:** GitHub Releases（9 章で決定）。Private のため利用者ごとの GitHub の認証が必要で、認証情報は EXE に埋め込まない。
  利用者が読み取り専用のトークンを一度だけ登録し、Windows の資格情報マネージャーに保存する。マニフェストはリリースに添付する。
- **チャンネル:** stable / development。stable は利用者が選ばない限り development を受け取らない。
- 実行中のファイルを直接上書きしない。アップデーター自身の更新は、次の起動時に入れ替える。

## 8. 技術の選択（案）

| 部品 | 案 | 理由 | 代わりの案 |
|---|---|---|---|
| ランチャー + モニター | 1 つのアプリ `SyncBridge.exe`（Python + PySide6、PyInstaller） | `session`、`protocol`、`launcher` のコードをそのまま使える。Maya のパネルと同じ Qt で見た目をそろえられる | ハブが配信する Web 画面（軽いが、ハブが止まっていると使えず、強制終了もできない） |
| 管理 API | ハブ（FastAPI）に追加 | 既存の仕組みに乗る | 別プロセス |
| アップデーター | `SyncUpdater.exe`（Python、PyInstaller、小さく保つ） | 仕様どおり。実行中のファイルを上書きしないため | ランチャーが自分で更新（実行中のファイルを置き換えられない） |
| 署名の検証 | `cryptography`（Ed25519） | 標準ライブラリにない | PyNaCl |

- PySide6 で配布物が 60〜80MB ほど大きくなる見込み（未計測）。PySide6 は LGPL なので、同梱の仕方に注意する（ライセンス文の同梱、動的リンク）。

## 9. 決定事項（2026-10-16、利用者の回答）

| 項目 | 決定 | 設計への影響 |
|---|---|---|
| 今後対応したいアプリ | **未定** | 特定のアプリに寄せず、4 章の一般的な仕組み（能力の申告、データ種別レジストリ）で受けられるようにする。アダプターは Python 系（Maya と同じ）と Adobe 系（AE と同じ）の 2 つのひな形を想定 |
| 更新の配布元 | **GitHub Releases** | Private のため、更新の確認・取得には利用者ごとの GitHub の認証が必要。トークンを EXE に埋め込まず、利用者が最初に一度だけ登録し、Windows の資格情報マネージャーに保存する（読み取り専用のトークン。方式は P-D で詳細設計）。リリースの作成は今どおり開発者が行う |
| ランチャーの形 | **普通のウィンドウ**（必要なときにスタートメニューなどから開く） | 常駐しない。更新の確認はランチャーを開いたときに行う |
| 進める順番 | **モニターから**: P-A → P-B → P-C → P-D、P-E は P-A と並行可 | 10 章の順 |

## 10. 段階計画（案）

| 段階 | 内容 | 依存 |
|---|---|---|
| P-A | ハブに管理 API、転送の履歴、ログの保持、ハブごとのセッションファイル。テスト | なし |
| P-B | モニター（ハブの一覧、接続中のアプリ、履歴、ログ、停止・強制終了・切断） | P-A |
| P-C | ランチャー（構成とバージョン、ハブの起動・停止、モニター、フォルダ） | P-B |
| P-D | アップデーター（マニフェスト、署名、適用、ロールバック） | P-C、9 章の 2 |
| P-E | ハブの一般化（能力の申告、データ種別レジストリ、新しい転送要求、後方互換） | P-A と並行可 |

- **決定した順番: P-A → P-B（モニター）→ P-C（ランチャー）→ P-D（アップデーター）。** P-E は P-A と並行して進められる。
- 仕様の Phase 2（設定の同期）は新しいデータ種別 `scene_settings` になるので、Phase 2 の前に P-E を終えておく。

## 11. P-A の実装（2026-10-16）

| 部品 | 場所 | 内容 |
|---|---|---|
| ハブごとのセッションファイル | `server/session.py` | `write_session` が `hubs/<pid>.json` と `session.json` の両方を書く。`read_hub_files()`、`remove_session(pid)` は両方を消す |
| 履歴・ログ・イベント | `server/hubstate.py` | `TransferHistory`（直近 200 件）、`LogBuffer`（直近 2,000 行、`syncbridge` と `uvicorn.error` のロガー）、`EventBus`（購読者ごとに 1,000 件、溢れたら古いものから捨てる） |
| 管理 API | `server/admin.py` | 5.3 の表のとおり。HTTP は `Authorization: Bearer <token>`、`WS /admin/events` は最初のメッセージ `{"token": ...}`（URL にトークンを入れない: アクセスログに残るため） |
| ハブの発見・強制終了 | `hubs.py`（標準ライブラリのみ） | `discover()`、`verify()`、`force_kill()`、`remove_stale()`、`admin_call()`。Windows のプロセス API は ctypes |

- **状態:** `running`（`/health` に応答し、確認済み）/ `not_responding`（プロセスはあるが応答しない、または確認できない）/
  `stale`（ファイルだけ残っている）/ `unknown`（ファイルのない `SyncServer.exe`）。
- **強制終了の確認（5.2）:** プロセスのイメージが `SyncServer.exe` か、ファイルに記録された `image` / `executable` と一致し、
  かつプロセスの作成時刻がファイルの `started` の 5 分前から 5 秒後までの間にあること（PID の再利用対策）。満たさなければ `ValueError` で何もしない。
- 停止時に接続中のアプリへ知らせる処理（5.2）とログのファイル出力（5.3）は P-B で追加した（12 章）。
- **0.1.x のハブ:** `session.json` しか書かないので、`discover()` は `session.json` も読む（`image` がないので、`SyncServer.exe` 以外は確認できず `not_responding` になる）。

## 12. P-B の実装（2026-10-16）

| 部品 | 場所 | 内容 |
|---|---|---|
| 表示の元（Qt なし） | `monitor/model.py` | 日本語のラベルと表の行、選んだハブの状態 `HubView`（イベントで更新）、`EventStream`（`/admin/events` を別スレッドで読む、標準ライブラリの WebSocket）、`load_hub()` |
| 画面 | `monitor/window.py` | PySide6 の普通のウィンドウ。上: ハブの一覧（5 秒ごとに自動更新）と「停止」「強制終了…」「残ったファイルを片付け」「ログフォルダを開く」。下: タブ「接続中のアプリ」（「切断…」）、「転送の履歴」（新しい順）、「ログ」（レベルで絞り込み） |
| 起動（開発） | `syncbridge-monitor.cmd`、`python -m syncbridge.monitor` | `.venv` に `requirements-monitor.txt`（`PySide6-Essentials`）が必要 |
| ハブのログファイル | `server/__main__.py`、`app.py` | `%LOCALAPPDATA%\SyncBridge\logs\hub-<pid>.log`。14 日より古いものはハブの起動時に削除。ハンドラーは lifespan で付ける（uvicorn が起動時にロガーを設定し直し、先に付けたハンドラーを外すため） |
| 停止の通知（5.2） | `server/admin.py` | `POST /admin/shutdown` は接続中のアプリに `error hub_stopping`（日本語の文）を送ってから止まる。切断は `error disconnected_by_admin`。Maya と AE のパネルはログに「error: <文>」と表示する（パネル側の変更なし） |

- ハブとの通信はすべて作業スレッドで行い、結果は Qt のシグナルで画面のスレッドに戻す（応答しないハブで画面が固まらない）。
- 操作はすべて確認ダイアログを出す。強制終了は `hubs.verify()` が通ったハブだけ有効（通らなければボタンを無効にし、理由をツールチップで示す）。
- **未確認:** インストール版（`SyncServer.exe`）での発見と強制終了、実際の Maya / AE パネルでの停止通知の表示。モニターの EXE 化は P-C（ランチャー）で行う。
